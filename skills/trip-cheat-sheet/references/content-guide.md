# 内容写作规范（content-guide）

> 这份规范回答一个问题：`trip.json` 里的内容**怎么写**，才能让用户在路上「打开就能用」。
> 字段的硬约束见 [`trip-schema.md`](./trip-schema.md)，完整示例见 [`../examples/tokyo-conference/trip.json`](../examples/tokyo-conference/trip.json)。

## 0. 先想清楚：三个视图各自服务什么

| 视图 | 用户此刻的问题 | 写作目标 |
|---|---|---|
| 行程（`days`） | 今天几点、去哪、为什么这样排 | 一眼看到「下一步动作」 |
| 清单（`checklists`） | 我别忘了什么 | 能勾选、能一键复制 |
| 手册（`handbook`） | 怎么走、多少钱、出问题找谁 | 能搜索、能照着做 |

写在行程里的内容，默认用户**已经在路上**：一只手拿手机、可能没网、可能赶时间、可能看不懂当地语言。
所以每个字的衡量标准是「能不能马上执行」，而不是「读完有没有收获」。

## 1. 五条总原则

| 原则 | 写法要求 | 做不到时的兜底 |
|---|---|---|
| 可执行 | 动词开头，给出对象与地点 | 写「到酒店前台确认」，不要留空 |
| 可核对 | 关键信息附来源链接与核查日期 | 标「待核实」 |
| 有取舍 | 写清为什么这样排、放弃了什么 | 写「备选：…」 |
| 留缓冲 | 转场留余量，不把一天排满 | 写「来不及就跳过 X」 |
| 不编造 | 价格、班次、开放时间、预约状态必须有来源 | 写「以官方为准」，宁缺毋滥 |

补一条隐性的：**不重复**。同一个事实只在最该出现的地方写一次（行程里写时刻，手册里写怎么走），避免两处修改不一致。

## 2. 事件的六要素

每条 `events[]` 至少回答六个问题：

| # | 要素 | 字段 | 写作要求 |
|---|---|---|---|
| 1 | 做什么 | `title` / `short` | `title` 写完整动作（「PEK → HND」），`short` 是时间轴用的 2–6 字标签（「飞东京」） |
| 2 | 几点 | `time` / `endTime` | 24 小时制 `HH:MM`，事件发生地的当地时间；有时段就写 `endTime` |
| 3 | 为什么 | `detail` 第一句 | 「为什么是现在/这里」，一句话即可 |
| 4 | 取舍提醒 | `detail` | 放弃了什么、备选是什么、代价是什么 |
| 5 | 缓冲 | `detail` + 时间安排 | 写清「最晚几点离开」，不要把转场卡到分钟 |
| 6 | 链接 | `links` / `map` | 官方来源优先：官网 > 官方社媒 > 大平台 > 攻略 |

### 2.1 反例与正例

反例（信息量低、无法执行）：

```json
{
  "title": "去机场",
  "detail": "早上去机场，坐飞机去东京。"
}
```

正例（有动作、有时刻、有取舍、有兜底）：

```json
{
  "time": "07:30",
  "endTime": "10:45",
  "tz": "Asia/Shanghai",
  "title": "PEK → HND",
  "short": "飞东京",
  "detail": "首都机场 T3 值机，建议 04:25 前到（国际航班提前到，以航司通知为准）。\n落地当地时间 11:45（东京比北京早 1 小时），入境+取行李约 45–60 分钟。\n如果延误超过 1 小时，直接跳过原定的机场午餐，便利店补给后去酒店。",
  "kind": "flight",
  "location": "北京首都国际机场 T3 → 东京羽田机场 T3",
  "map": { "query": "北京首都国际机场T3", "mode": "transit" },
  "links": [ { "label": "航班动态", "href": "https://www.flightradar24.com/" } ],
  "checkId": "check-flight"
}
```

> 关于航班 `endTime` 的时区：渲染器把 `endTime` 也按事件的 `tz` 解释（见 §3.2）。
> 想省掉换算，优先把起飞、落地拆成两条事件，各自用当地时区。

### 2.2 `detail` 的写作公式

```
动作（做什么）+ 关键信息（几点/在哪/带什么）+ 为什么/取舍 + 兜底（出问题怎么办）
```

- **长度**：1–4 句；换行在 JSON 字符串里写 `\n`（渲染后是真正的换行）。
- **折叠提示**：行程页把 `detail` 收进「详情」折叠区，一屏可见的是时间、标题、标签、地点和按钮。所以关键动作要写进 `title` / `short` / `location`，不要只写在 `detail` 里。
- **顺序**：最重要的信息放第一句；「为什么」可以放最后，但不要省略。
- **数字**：票价、班次、时长、距离必须来自来源；估算值写「约」并说明是估算。
- **人称**：用第二人称「你」或无人称祈使句；不要用「我们建议您」这类公文腔。
- **语气**：平实、克制。不用「绝美」「必去」「不容错过」等营销词，也不用「据说」「应该」。
- **术语**：中文 + 当地文字/英文原名（如「京急空港线（京急空港線）」），方便给司机看、方便现场找。

### 2.3 缓冲时间怎么估

- **转场**：按地图估时再加 30–50% 余量；换乘多、带行李、语言不通时更多。
- **机场**：按航司/机场的官方建议提前到，不要凭感觉写；转机时间低于机场建议的最短转机时间时，明确写「风险」。
- **会议/景点**：提前 15–20 分钟到门口（安检、找厅、找座位都要时间）。
- **每天**：至少留 1 个「空档」（可休息/可补漏），不要从早排到晚。
- **硬约束优先**：有预约/有固定时刻的事项（航班、门票、会议）先固定，其他围绕它排。

### 2.4 一天的节奏（day 级写法）

- `days[].title`：写「基调」，不写流水账。例：「出发 · 抵达东京」「会议第一天：注册 + 开幕」。
- `days[].note`：当天整体提示，1–2 句。例：「今天不排景点，落地后只做入住和补给。」
- 每天最多 **2–3 个硬事项**（必须按时发生的），其余是软事项（可跳过/可调整）。
- 时间线不能重叠；`events` 按时间先后写（渲染器会再排序，但源文件保持可读）。

### 2.5 路线、餐厅、住宿：三个必须验证的选择

这三件事最容易「看起来合理、到现场翻车」。写进行程前先验证，验证结果写进 `detail` 与 `links`，并注明核查日期。

#### 2.5.1 路线：用地图软件核验，不靠攻略估

| 核验什么 | 怎么核验 | 写法示例 |
|---|---|---|
| 交通方式与耗时 | Google Maps / 高德 / 腾讯地图（国内）；当地交通运营方官网/App（轨道、机场巴士）；步行距离用「步行」模式 | 「地铁 X 线 → Y 站换乘，约 35–45 分钟（地图核验于 2026-11-08）」 |
| 末班车/首班车 | 运营方官网或站内时刻表；夜间到达必须查 | 「末班车 00:20；若晚于 23:30 到达建议打车」 |
| 换乘与步行 | 换乘次数、站内步行、出口编号、电梯/无障碍 | 「Y 站 3 号出口步行 6 分钟」 |
| 实时波动 | 高峰、雨天、施工、罢工；给区间不给单点 | 「约 30–50 分钟，早晚高峰取上限」 |

- 地图软件给的是**平峰估算**：带行李、带老人小孩、语言不通时再加 30–50% 余量（见 §2.3）。
- 跨城、国际航班、机场接驳以**运营方官方**为准，地图可能只给「驾车」方案。
- **没核验就标「待核实」**，不要直接抄攻略里的「大约 20 分钟」；核验日期写进 `detail` 或 `meta.footer`。
- `map.mode` 与实际推荐方式保持一致（步行/公交/驾车），页面会按它生成地图深链。

#### 2.5.2 餐厅：评分 + 小红书 + 能不能订

三源交叉，缺一不可：

| 来源 | 看什么 | 可信度 |
|---|---|---|
| 平台评分 | 大众点评 / Google / 食べログ / OpenTable 的分数、评价数、**最近评价** | 参考（可能有刷分/过时） |
| 小红书 / 社区 | 真实体验、排队、点单、踩坑、最新变化 | **个人体验，待核实**；不能当唯一证据 |
| 官方 / 预订页 | 营业时间、休息日、**能否预约**、预约渠道、取消规则、着装 | 已确认（记录核查日期） |

- **必须确认能否预约**：能预约的写预约方式（官网/电话/平台）与建议时间；不能预约的写排队规则和建议到达时间；约不上的热门店给备选。
- 人均、必点、忌口/过敏、着装（是否需正装）写进 `detail`；预约名/号码放 `copy` 占位符。
- 引用小红书要标「个人体验」并附来源链接，避免「全网都说」「必吃」这类表述。
- 营业信息会变：写核查日期，并在 `meta.footer` 提醒出行前复核。

#### 2.5.3 住宿：先定优先级，再验三件事

先和用户确认优先级，再选酒店：

1. **效率优先**：离会场/核心景点近（步行或 1–2 站），减少每天通勤；
2. **夜间生活优先**：晚上逛街、吃饭、便利店/药妆方便，回酒店安全；
3. **报销合规优先**：公差住宿标准、发票类型、是否必须协议价/公司渠道；
4. **预算优先**：在上述约束内选性价比。

验证清单：

| 维度 | 要核验 | 写入位置 |
|---|---|---|
| 通勤 | 到会场/景点的步行/地铁耗时、末班车、雨天方案 | 入住事件 `detail` + `map` |
| 夜间生活 | 周边餐饮/便利店/药妆/购物营业到几点；夜间步行安全 | `detail` 或 `handbook`「住宿」章 |
| 报销 | 能否开票（增值税发票/收据/水单）、抬头税号、住宿标准上限、预授权/押金、退改政策 | `checklists`（发票/押金）+ `handbook`「住宿」章 |
| 入住细节 | 入住/退房时间、早餐、行李寄存、Wi-Fi、床型/无烟房 | `detail` + `copy` |

- `detail` 里写一句**决策记录**：「选这里因为离会场步行 10–15 分钟、晚上银座吃饭购物方便；放弃了更便宜的郊区酒店（每天多 40 分钟通勤）。」
- 报销写进清单：退房前确认发票、保留水单、拍照归档（见 `handbook`「住宿」章示例）。
- 需要用户确认的：公司差旅标准/发票抬头税号/是否必须走公司订房渠道——不要替用户假设。

### 2.6 公差 / 私差 / 混合：先定性质，再定写法

`meta.tripType` 取 `business`（公差）、`leisure`（私差）或 `mixed`（混合）。不填也可以，但**先问清楚**：它决定住宿约束、日程密度、清单与手册要放什么，以及哪些内容能公开。

| | **公差 business** | **私差 leisure** | **混合 mixed** |
|---|---|---|---|
| 目标排序 | 准点、效率、报销合规 | 体验、预算、灵活 | 分段：公差段照公差，私人段照私差 |
| 住宿约束 | 公司住宿标准、协议酒店/渠道、发票抬头税号、预授权/押金、近会场 | 预算、地段（近景点/夜生活）、可退改 | 公差段按公司标准，私人段可另选；**分开订、分开开票** |
| 日程密度 | 硬事项优先，少排景点，留体力 | 可多排、可晚归、可临时调整 | 按「公差段 / 私人段」分天写，避免混在一天里 |
| 手册必备 | 报销与票据、参会/证件、着装、名片/材料 | 门票预约、交通卡、保险、紧急电话、购物退税 | 两者都要，且标明哪章服务哪一段 |
| 清单必备 | 审批单、行程单、发票抬头/税号、公司卡、差旅平台订单 | 门票/餐厅预约、证件复印件、保险单 | 分段列出，发票类只列公差段 |
| 隐私 | 会议内部信息、客户信息不上公开页；票码/证件不公开 | 主要是个人票码与住址 | 公差段敏感信息更难处理：建议只本地保存或密码门 + 私有托管 |
| 语气 | 克制、执行导向 | 可以更生活化 | 分段切换，不要用公差的语气写度假段 |

**混合行程的三条硬规则**

1. `meta.footer` 写明「X 月 X–X 日为公差（参会），X–X 日为私人行程」，`days[].note` 也标一下；
2. 发票、行程单、审批单只覆盖公差段；私人消费不写进报销清单，避免口径混淆；
3. 日程按段排：公差段围绕会议硬约束，私人段再排景点/购物/餐厅；两段之间留转场缓冲。

**公差最容易漏的四件事**：发票抬头与税号（`copy` 占位）、行程单/审批单（部分公司报销必需）、公司卡与个人垫付的分开记录、住宿是否必须走协议渠道（自己订可能不报）。

## 3. 双时区与跨日写法

### 3.1 基本规则

1. `meta.home.tz` 是常驻地时区（如 `Asia/Shanghai`），`destinations[].tz` 是目的地时区（如 `Asia/Tokyo`）。
2. 每条事件的 `time` 写**该事件发生地的当地时间**；`tz` 不填时继承 `day.destination` 的时区。
3. 页面会自动把每条事件换算成常驻地时间并显示（如「07:30 东京 · 06:30 北京」），**正文里不要再手写一遍换算**。
4. 全天的无时刻安排（如「自由活动」「休息」）用 `skipTimezone: true`，避免显示没有意义的换算。
5. `tz` 一律写 IANA 名称（`Asia/Tokyo`、`Europe/Madrid`），不要写 `UTC+9`、`JST` 这类偏移或缩写。

### 3.2 航班与跨时区事件

| 场景 | `time` / `endTime` | `tz` | 备注 |
|---|---|---|---|
| 出发地起飞（推荐拆条） | 起飞当地时间 | 起飞地时区 | `title` 写「PEK → HND」，`detail` 写落地当地时间 |
| 落地（推荐拆条） | 落地当地时间 | 落地地时区 | 放在落地当天的 `day` 里；跨日就放次日 |
| 合并成一条（可选） | `time` = 起飞当地时间；`endTime` = **落地时刻换算到起飞地时区**后的时间 | 起飞地时区 | 必须在 `detail` 写清「落地当地时间 HH:MM」 |
| 中转（同一天第三时区） | 该机场当地时间 | 该机场时区 | 中转时长按真实时间算，别用目的地时区套 |
| 当地会议/用餐 | 当地时间 | 可不填（继承当天目的地） | 不要为了「统一」而改成北京时间 |

合并航班事件时，**最容易错的点**是 `endTime`：它和 `time` 共用 `tz`。例：北京 07:30 起飞、东京 11:20 落地，东京比北京早 1 小时 → `endTime` 应写 `10:20`（北京时间），并在 `detail` 里写「落地当地时间 11:20」。

### 3.3 跨日与跨夜

- `day.date` 用事件**发生地的日期**：北京 23:00 起飞，`date` 是北京日期。
- **跨日到达**：把到达事件放进次日 `day`（或新开一天），`detail` 写「+1 天」「次日」。
- **跨午夜**：`endTime` 小于 `time` 时渲染器会自动按次日处理；仍建议在 `detail` 写「次日凌晨」，方便阅读。
- 红眼航班、通宵火车尽量拆成「起飞/上车」与「到达」两条，避免读者误判日期。
- `days` 要覆盖行程中的每一天（含中转日、休息日），不要跳日，否则时间线会断档。

### 3.4 夏令时（DST）

- 出行日期落在 DST 切换日附近时，在 `detail`/手册里写明「当地 03:00 → 02:00（时钟回拨）」这类变化，并提醒保持手机自动时区。
- 切换日可能出现同一个本地时刻出现两次；不确定就改用「事件级 `tz` + 真实时间描述」，并在手册标注。
- 构建器会用 `Intl.DateTimeFormat` 校验时区合法性，但**不会**替你判断 DST 的业务影响——这是写作责任。

### 3.5 正文里什么时候手写「北京时间」

页面已自动显示双时区，正文默认不重复。只有这些情况值得手写：

- 需要在**出发前**按北京时间行动（如「值机于北京时间 10 月 20 日 07:25 开放」）。
- 跨日/跨时区容易算错的会议或预约（写一次「对应北京时间」即可）。
- 与国内同事协作的时间点（远程会议、直播）。

写就写全（日期 + 时区），并和页面显示保持一致；不要一处写东京时间、一处写北京时间。

## 4. 清单（`checklists`）规范

- **分组**：`出发前` / `落地后` / `会议期间（或每日）` / `返程前`，按行程阶段分，不按主题分。
- **每项一件事**：标题是动作（「值机并保存登机牌」），`detail` 给可执行细节（开放时间、在哪、存哪）。
- **`copy` 字段**：只放「需要复制去别处用」的短文本（地址、预约号、电话）；用 `<占位符>` 表示敏感信息。
- **`checkId`**：与行程事件关联（如领证事件 ↔「领参会证」清单项），点击事件即可勾选。
- **`id` 全局唯一**；清单项不要写成任务管理器的长列表，一个阶段 4–8 项足够。
- **勾选状态只存本机浏览器**（localStorage），不要写「已同步」「云端保存」这类不存在的承诺。

## 5. 手册（`handbook`）规范

手册是「到了当地才用」的部分：怎么走、怎么连网、怎么付钱、出事找谁。

- 每章 2–4 节；每节讲清**一个动作**（怎么从 A 到 B、怎么买票、卡刷不了怎么办）。
- `html` 只允许基础标签（`p/ul/ol/li/b/strong/em/a/br/code/mark/small`），生成器会做白名单清洗。
- `copy` 放最常被复制的内容：地址（当地文字）、预约号、电话。
- 不要写百科式背景介绍；把「为什么」压缩成一句，重点写「怎么做」。
- 电话、地址、营业时间这类会变的信息，标注来源与核查日期。

### 5.1 章节清单（默认 8 章；公差/混合再加 `expense` 报销与票据）

| 章节 id | 标题 | 至少包含 | 常见 `copy` 字段 |
|---|---|---|---|
| `transport` | 交通 | 机场 ↔ 市区（各方式+末班车）、市内交通、交通卡/票券、打车注意 | 酒店地址、车站名 |
| `stay` | 住宿 | 入住/退房时间、早餐、行李寄存、Wi-Fi、**发票与报销**、押金/预授权、退改政策、周边夜间便利 | 酒店地址（当地文字）、确认号占位、前台电话 |
| `expense` | 报销与票据（公差/混合必选） | 发票类型与抬头税号、行程单/审批单、公司卡与个人垫付、报销时限、票据归档 | 发票抬头、税号、审批单号占位、报销平台 |
| `network` | 网络与通讯 | eSIM/漫游/当地卡、免费 Wi-Fi、常用 App、紧急联系人 | 酒店 Wi-Fi 密码占位、领保电话 |
| `payment` | 支付与货币 | 卡组织覆盖、现金/ATM、移动支付、小费/退税 | 酒店电话、卡挂失电话 |
| `safety` | 安全与应急 | 报警/急救/火警电话、医院/药店、使馆与领事保护、丢证件处理 | 使馆地址电话、保险救援电话 |
| `conference` | 参会与证件 | 领证时间地点、议程与场地分布、海报/讲者须知、着装、胸牌 | 注册号占位、会场地址 |
| `food` | 饮食 | 已订餐厅、忌口/过敏、营业时间、便利店/超市、饮水 | 餐厅地址、预订名 |
| `packing` | 打包与穿着 | 天气与衣物、正式程度、药品、转换插头、行李规则 | 酒店地址 |

可选章节：`language`（语言与礼仪）、`shopping`（购物与退税）、`sights`（景点预约与看点）。

> 章节可以合并或增补，但主题别漏。示例数据 `examples/tokyo-conference/trip.json` 把「饮食」和「打包」合并成一章，并额外加了「时间与时区」一章。

## 6. 已确认、待核实、未定、示例：标注规则

`trip.json` 没有「核实状态」字段，统一用**固定措辞**在文字里标注，便于肉眼识别和搜索。

| 状态 | 什么情况 | 推荐写法 | 示例 |
|---|---|---|---|
| 已确认 | 用户提供的预订/确认单，或官方页面（写明核查日期） | `已确认：…` 或直接陈述 + 来源链接 | 「已确认：10:00 入馆，预约号见清单」 |
| 待核实 | 第三方平台、旧截图、攻略、电话未接通 | `待核实：…` +「以官方为准」 | 「待核实：周末 20:00 关门（来源：攻略，官网未确认）」 |
| 未定 | 还没有安排 | `未定：…` /「当天再定」 | 「未定：午餐在会场附近解决」 |
| 示例 | demo 数据、占位内容 | `示例：…` | 「示例：航站楼 T3，以登机牌为准」 |

规则：

1. 只标注「会变、会花钱、会卡住」的字段：时刻、价格、预约、开放时间、地址、电话、签证/入境要求。
2. 不要每句都标；一屏里最多 1–2 处，否则读者会忽略。
3. `meta.footer` 统一写数据截止日期与复核提醒，例：「内容截至 2026-11-10，出行前请复核航班、预约与营业时间」。
4. 用词统一，不要混用「据说」「应该」「大概」「可能」。
5. 「已确认」必须有来源（链接或用户原文），不能凭印象写。
6. **小红书/攻略/社区评价 = 个人体验**：写「个人体验」或「待核实」，不能当作「已确认」；餐厅/酒店的**预约状态只以官方或预订渠道为准**，并写上核查日期。
7. 平台评分只能作参考（可能刷分/过时）；引用时给平台与评价数，例如「Google 4.3★（88 条评价，2026-11-08 查）」。

## 7. 调研优先级与常见坑

### 7.1 调研优先级

| 优先级 | 内容 | 为什么先做 |
|---|---|---|
| P0 | 签证/护照有效期、航班/车次、住宿、会议注册/门票、保险 | 不成立则行程不成立 |
| P1 | 机场 ↔ 市区交通、市内交通票、门票分时预约、餐厅预订 | 决定体验和当天节奏 |
| P2 | 景点、购物、备选餐厅、天气 | 可现场调整 |

调研顺序建议：先用官方页面确认 P0 → 再查 P1 的官方规则（预约、末班车、换乘）→ 最后补 P2。
每条结论记下来源 URL 和核查日期，直接写进 `links` 或 `meta.footer`。

住宿、餐厅、路线这三类候选按 **§2.5** 做三源验证：路线用地图软件核验；餐厅看平台评分 + 小红书 + 官方预约渠道；住宿核对通勤、夜间便利与报销条件。攻略类内容只能当线索，不能当结论。

### 7.2 常见坑（逐项写进手册或事件的 `detail`）

**机场交通**

- 同一城市多航站楼（T1/T2/T3 之间可能要摆渡/地铁），落地后先确认航站楼。
- 末班车/首班车时间；夜间到达时公共交通可能已停运。
- 行李多、带娃、老人优先出租车/机场巴士，不要硬挤地铁换乘。
- IC 卡有押金和退卡规则；机场快线可能全车指定席、需另购特急券。
- 入境排队时间波动大，转机不要把时间卡到最短。

**门票预约**

- 分时预约（选到具体时段）、实名（护照/身份证）、闭馆日、旺季售罄。
- 动态二维码需要联网；截图可能无效；现场换票窗口位置。
- 学生/老人票要带证件；免费日/夜场规则不同。
- 预约确认邮件离线保存一份。

**Wi-Fi / 网络**

- 免费 Wi-Fi 常需短信验证码，境外手机号可能收不到；提前准备 eSIM/漫游。
- eSIM 出发前安装好，落地再启用；确认手机支持且不锁网。
- 提前下载离线地图与翻译包；VPN 的合规性按目的地要求处理，不要写「随便用」。
- 把酒店 Wi-Fi 密码、紧急联系人写进手册 `copy`。

**支付**

- 卡组织覆盖差异（Visa/Mastercard/银联/JCB）；磁条卡、免密、签名规则。
- 移动支付（Apple Pay/Google Pay/当地钱包）开通条件；小额现金备一点。
- 小费文化（哪些国家/场景）；DCC 动态货币转换（选当地货币结算）。
- 退税流程、最低消费、离境前办理窗口；卡冻结/挂失电话存进手册。

**紧急电话与安全**

- 报警/急救/火警各国不同，写具体号码（不要只写「打 110」）。
- 中国领事保护与服务应急热线 **12308**；写清中国驻当地使领馆地址与电话。
- 酒店前台、保险救援、信用卡挂失三个号码放进 `safety` 章的 `copy`。
- 丢证件/丢卡的处理顺序（报警 → 联系使领馆/银行 → 保险报案）。

**会议**

- 领证时间与地点（可能不在主会场）；胸牌是通行凭证，别放行李箱。
- 展厅与分会场可能在不同楼；海报挂取有固定时段与尺寸要求。
- 注册确认邮件、议程 PDF 离线保存；线上会议注意双时区换算。
- 着装要求（商务/商务休闲）；会场网络与充电位紧张。

**时区与节假日**

- DST 切换日、红眼航班、跨日到达、跨时区远程会议（双闹钟）。
- 当地公共假期/宗教节日闭馆或缩短营业；交通/机场罢工；游行与大型活动封路。

**语言与现场**

- 地址给司机看当地文字版本；菜单/门票截图；基础问候语。
- 紧急时找「i」信息台、车站工作人员、酒店前台，比问路人更可靠。

**路线、餐厅与住宿**

- 路线必须用地图软件核验，写清时间区间、末班车、步行距离，并标核验日期（§2.5.1）；不要直接抄攻略里的「约 20 分钟」。
- 餐厅必须确认评分来源、能否预约、排队规则、休息日与取消规则（§2.5.2）；小红书只能作个人体验参考。
- 住宿必须核对通勤、夜间生活便利、报销/发票/押金要求，写清选择理由与放弃项（§2.5.3）。
- **先定公差/私差/混合（§2.6）**：性质不同，住宿约束、清单与手册模块都不同；混合行程必须分段标注，发票口径只覆盖公差段。

## 8. 隐私与红线

- **不写真实票码/二维码/PNR/证件号/手机号/门牌号/他人姓名**进即将公开的页面。
- `copy` 字段用占位符（`<PNR>`、`<预约号>`、`<酒店确认号>`），由用户在本机替换后再构建。
- 公开站点等于任何人（含搜索引擎）可见；需要分享真凭证时用密码门 + 私有托管，并了解密码门只是前端校验（见 [`deploy.md`](./deploy.md)）。
- 示例数据必须虚构、脱敏；仓库里的二维码只放占位图。
- 不要写对他人隐私的推断（同行人身份、健康信息、行程目的等），除非用户明确要求且知情。

## 9. 发布前自检清单

跑 `node scripts/verify.mjs <trip.json>` 之前，先人工过一遍：

1. 时间线无重叠；每段转场有时间余量。
2. 每条事件有 `title` + `time`；有地点的事件有 `location`，能导航的有 `map`。
3. 航班/跨时区事件的 `tz` 正确；跨日事件已放到次日或写清「+1 天」。
4. 价格、班次、开放时间、预约状态都有来源或明确标「待核实」。
5. `links` 全部可打开、是官方/可靠来源，没有死链。
6. 「已确认 / 待核实 / 未定 / 示例」用词统一。
7. `meta.startDate ≤ 每个 day.date ≤ meta.endDate`；`days` 覆盖全程无断档。
8. 所有 `tz` 是 IANA 名称，不是偏移或缩写。
9. `checklists` 的 `id` 全局唯一，`checkId` 都能在清单里找到对应项。
10. `handbook` 的 `html` 只用白名单标签；8 章齐全（交通/住宿/网络/支付/安全/参会/饮食/打包）。
11. `tickets` 的 `qr` 只指向占位图；`person` 能区分同行人。
12. `copy` 字段无真实敏感信息。
13. 手机竖屏读一遍：一屏内能看懂「下一步」。
14. `meta.footer` 写了数据截止日期与复核提醒。
15. `verify.mjs` 零错误；警告要么修掉，要么能解释。
16. 路线用地图软件核验过，写清时间区间/末班车/步行距离与核验日期（§2.5.1）。
17. 餐厅评分有来源、预约/排队/休息日已确认；小红书引用标了「个人体验」。
18. 住宿写了选址理由（效率/夜间生活/报销/预算）、通勤方案、报销/发票/押金要求；清单里有对应提醒。
19. `meta.tripType` 已确认；公差/混合有「报销与票据」章与发票抬头/行程单/审批单占位，私差不硬塞报销内容。
20. 混合行程已分段标注（哪几天公差、哪几天私人），发票口径只覆盖公差段，敏感会议信息未进公开页。
